# Runtime Specification, version 0.7

Status: **Draft, implemented**. Normative for the reference interpreter and for
every backend that executes Agent IR.

Runtime 0.7 is [Runtime 0.6](./v0.6.md) plus one thing:

1. **a failure an iteration can absorb** — a call node may carry a `fallback`
   value, and what a fallback is permitted to stand in for is a short, closed
   list.

Execution semantics, budgets, policy enforcement, concurrency, cassettes,
artifacts and every other event are inherited from 0.6 and earlier unchanged.

Design reasoning is in
[RFC-0022](../../rfcs/0022-a-failure-an-iteration-can-absorb.md).

## 1. What this changes, and what it does not

Before 0.7, every failure ended the run. That is the right behaviour for work
whose job is to produce something correct or nothing, and it stays the default:
**a node with no `fallback` behaves exactly as it did.**

The problem 0.7 addresses is one shape, and it is the most ordinary one there is.
A fan-out over partial data loses one element and, because iterations are drained
rather than cancelled ([§3.4 of 0.6](./v0.6.md)), **spends the whole fan-out and
returns nothing.** A run that burns tokens to produce a non-result is not a
missing convenience.

## 2. A fallback

A node of kind `llm.call`, `tool.call` or `agent.call` may carry a `fallback`, a
pure [`Value`](../ir/v0.1.md) ([Agent IR 0.4 §2](../ir/v0.4.md)). When the attempt
at that node fails and §2.1 permits it, the runtime binds the fallback's value to
the node's `binding` and execution continues from `next`.

A `fallback` on any other node kind is a **malformed artifact**. A runner must
refuse it. Refusing before the run starts is better than refusing at the node,
because an artifact that is going to be refused should be refused before it spends
anything.

### 2.1 What a fallback may not absorb

**This is the most important rule in this document, and it is not about
ergonomics.** A backend that got it wrong would turn every guarantee in this
language into a default value, silently.

A fallback stands in for a failure of the **attempt**: a tool that ran and failed,
a tool that returned something that is not its declared type, a provider that
could not be reached, a provider that rejected the request or rate-limited it, a
provider that declined to answer, an answer that was cut off, an answer that did
not match its declared type, and a sub-agent whose own failure was one of these.

It **must not** stand in for any of the following.

| Not absorbed | Because |
|---|---|
| a capability the policy denies, or grants no rule for | The artifact's own statement about what it may do. If a fallback routed around it, `deny` would become advisory — which is the one thing this project exists to refuse. |
| a budget that ran out | A budget bounds the **run**, not a statement. A statement that could absorb one would make a budget a suggestion with extra steps. |
| an approval a person refused | A person said no. Continuing with a default is continuing without them. |
| a `verify` that did not hold | The failure most worth recovering from and the one where recovering is most suspect: the property the artifact states either holds or the run is not entitled to its output. |
| a malformed artifact | Not a failure of the world; a failure of the program. |
| a recording that no longer matches this run | A stale cassette. Absorbing it would let a test pass on a digest of defaults after somebody edited a prompt, which is the exact failure the request digest exists to prevent. |
| a missing credential or an unusable model | A setup mistake somebody can fix. A run with no key that produced a digest of defaults would look like a run that worked. |
| a tool no host provides | The artifact requires the tool. This is a host that was not wired up, not a call that failed. |
| a question a person did not answer | `else` cannot attach to a `consult` at all ([Language 0.4 §1.3](../language/v0.4.md)); stated here so the guarantee does not depend on where a compiler put a node. |

**A sub-agent is checked recursively.** A caller absorbs a callee's failure only if
the callee's failure was itself absorbable. Otherwise moving a denied call into a
sub-agent and putting a fallback on the caller would absorb the denial after all —
and a callee's step budget is bounded by what remains of its caller's, so a
callee's exhausted budget is the caller's budget in disguise.

*How to implement this.* Not as a comparison of message text. The reference
interpreter matches on its error type with no wildcard arm, so a new failure kind
does not compile until somebody has decided which side of this table it falls on.
The generated Python program inverts the same idea: a failure is unabsorbable
unless something marked it otherwise, and only the provider call and its
validation do — so a failure nobody classified is refused rather than absorbed. A
forgotten classification must cost a run that stops when it could have continued,
never a guarantee that quietly became a default.

### 2.2 `fallbackTaken`

A recovered failure **must** be visible. A run that quietly succeeded on a default
is a run whose record does not say what happened, and the record is what this
language is for.

```json
{"event":"fallbackTaken","node":"n4","because":"model"}
```

| Field | |
|---|---|
| `node` | the node whose attempt failed |
| `because` | the kind of failure: `model`, `tool` or `agent` |

`because` is taken from the **node kind**, not from the error — `llm.call` →
`model`, `tool.call` → `tool`, `agent.call` → `agent` — so its value is the same
on every backend and for every way one kind of node can fail. It never carries the
failure's text, which is already in the events before it.

Emitted **after the failing node's own events and before execution continues.** A
failed attempt emits no `modelCall` or `toolCall` event, because it did not
succeed; so in the stream, a fallback reads as a `nodeStarted` followed directly by
a `fallbackTaken`.

A reader counting `fallbackTaken` events knows how much of a result was made of
defaults, which is the first question to ask of one.

## 3. Inside a fan-out

Nothing about a fallback is special inside a `parallel` node, and that is what
makes it work. The iteration does not fail, so the fan-out does not fail, and the
collected list **keeps one entry per element**.

Under an overlapping schedule ([0.6 §3.1](./v0.6.md)) a `fallbackTaken` is spliced
into the stream in index order like every other event, at the position a
sequential run would have put it. §3.4 of 0.6 is unchanged and now applies to a
smaller set of failures: an iteration that absorbed its own failure never became a
failing iteration.

## 4. Steps, tokens and cost

**The attempt is the step, charged exactly once**, whether or not the fallback was
used. A fallback is a value, and evaluating a value is not a step — so the bound
the compiler proved from a bounded walk of the graph does not move.

Tokens and money are charged from what a call returned. A call that failed returned
nothing and adds neither. This is inherited behaviour, and it has a consequence
worth stating: **a run's recorded token total can be lower than what the transport
was billed for**, when an answer arrived and was then rejected. The record says
what the run used, not what the connection spent. A backend must not invent a
charge to close that gap — a number nobody can reproduce is worse than a number
that is honestly narrow.

## 5. Evaluating the fallback

A fallback is pure, so evaluating it cannot fail in any way this section needs to
describe, and it cannot be observed except through the value it produces.

A read the fallback needs — of an input, a binding, `state` or `memory` — is
performed whether or not the fallback is taken. Reads are idempotent, so this
changes no value, and it keeps the sequence of nodes in the record identical
between a run that fell back and one that did not. `fallbackTaken` is then the
only difference between the two, which is what makes it worth counting.

## 6. Conformance

The case `fallback-taken` holds a backend to §2.1, §2.2, §3 and §4 at once: an
answer that did not match its declared type, absorbed inside a fan-out, with the
event in the right place and one entry per element in the result.

It replays from a **cassette 0.3** recording, because the format did not move. See
[Agent IR 0.4 §5](../ir/v0.4.md) for what a 0.3 recording can and cannot hold, and
[GAP-046](../../docs/gaps.md#gap-046) for the half it cannot.
