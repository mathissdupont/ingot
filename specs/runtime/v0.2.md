# Runtime Specification, version 0.2

Status: **Draft, implemented**. Normative for the reference interpreter and for
any backend that emits the event stream described here.

Runtime 0.2 is [Runtime 0.1](./v0.1.md) with two changes:

1. a `verify` node reports **what it did** rather than a boolean that could only
   describe one of three outcomes;
2. a cassette records **tool calls** as well as model exchanges, so an offline
   replay can cover an agent that uses tools.

Execution semantics, budgets, policy enforcement, artifacts and every other event
are inherited from 0.1 unchanged.

## 1. `verified` carries an outcome

In 0.1 the event was:

```json
{ "event": "verified", "node": "n7", "verifier": "CitationCheck", "passed": true }
```

In 0.2 it is:

```json
{ "event": "verified", "node": "n7", "verifier": "CitationCheck", "outcome": "notPerformed" }
```

`passed` is **removed**. `outcome` is required, and must be one of:

| Value | Meaning |
|-------|---------|
| `notPerformed` | The backend has no implementation for this verifier. The property is unchecked. |
| `passed` | The check ran and the property held. |
| `failed` | The check ran and the property did not hold. |

A backend **must not** report `passed` for a check it did not perform. Agent IR
records a verifier's name and signature and carries no representation of the
check itself ([Agent IR 0.1 §6](../ir/v0.1.md)), so a backend with no verifier
implementation **must** report `notPerformed`.

`notPerformed` is not a failure. A consumer deciding whether a run met its
declared properties must treat `notPerformed` as *unknown* and must not fold it
into either `passed` or `failed`. Treating it as a failure would be the mirror of
the bug this revision fixes.

Executing a verifier remains optional, and a `verify` node still does not stop a
run. What changed is only what the run is allowed to claim.

### Why the field was replaced rather than extended

Adding `performed: true|false` beside `passed` would have left the misleading
field in place for every consumer that already read it, and made the honest
answer the one you get by reading two fields in the right order. Removing
`passed` makes the wrong reading impossible rather than merely discouraged.

This is a breaking change to a documented event stream, taken at the only point
in the project's life where it is free: nothing has been released
([GAP-022](../../docs/gaps.md#gap-022)), so no consumer of Runtime 0.1's
`verified` event exists outside this repository.

## 2. Cassette 0.2 records tool calls

A 0.1 cassette holds the model exchanges of a run and nothing else, so replaying
one leaves a tool call with nowhere to go. 0.2 adds a `toolCalls` list:

```json
{
  "cassetteVersion": "0.2",
  "agent": "heptapus.examples.digest.RepoDigest",
  "inputs": { "directory": ".", "out": "out/digest.md" },
  "interactions": [ … ],
  "toolCalls": [
    {
      "index": 0,
      "node": "n0",
      "tool": "fs.list_dir",
      "invocationDigest": "…",
      "resultType": "string[]",
      "value": ["README.md", "notes.md"]
    }
  ]
}
```

| Field | Meaning |
|-------|---------|
| `index` | Position in this list. |
| `node` | The IR node that made the call. |
| `tool` | Bare tool name, as the artifact declares it. |
| `invocationDigest` | Digest of everything that determined the answer (§2.1). |
| `resultType` | The Ingot type the tool is declared to return. |
| `value` | What the tool returned. Absent when the call failed. |
| `error` | The failure, when there was one. Absent otherwise. |

Exactly one of `value` and `error` must be present. A recorded failure is
replayed as a failure: how an agent behaves when a tool fails is the behaviour
most worth having a test for, and a format that could only hold successes would
be a format for the happy path.

`toolCalls` is matched **independently of `interactions`**, by position within
its own list. An agent may make three tool calls between two `ask`s, and a single
interleaved stream would make each side's position depend on the other's.

### 2.1 The invocation digest

`sha256` over, in order and NUL-separated: the calling agent's fully qualified
name, the transport-qualified tool reference, the declared result type, and each
argument as `name` then its canonical JSON value in key order.

The agent is included because two agents in one program deliberately hold
different policies, so the same call made by a different agent is a different
call. Declared effects are **not** included: they say what a call is permitted to
do, not what it answers.

A replay must compare the digest and **refuse** on a mismatch, naming the call.
A changed argument means the recorded answer is for a different question.

### 2.2 A replayed tool call does not perform the effect

Replay returns the recorded result. It does not start a server, reach a network,
or write a file — that is the entire point of an offline test. An agent whose
recorded run wrote a file will, on replay, receive the handle that write produced
and leave the filesystem untouched.

This is a property to rely on and a limit to know: `ingot test` proves what the
agent *does with* a tool's answer, not that the tool still answers that way.
Checking the second is what a live run is for.

### 2.3 Reading a 0.1 cassette

0.2 is a superset, so a 0.1 recording is a valid 0.2 one with no tool calls and
keeps replaying unchanged. A producer writes 0.2. A document that states `0.1`
and carries `toolCalls` must be refused rather than read: it was written by
something that did not mean 0.1.

### 2.4 What a recording contains

Whatever the tool returned. A cassette is committed and reviewed, and a tool
result is the one part of it that came from outside the repository. A producer
must scan cassettes for credential-shaped values alongside source and IR
([Ingot Package 0.1 §8](../image/v0.1.md)).

## 3. Compile-time notice

A compiler that knows no backend in its toolchain can perform a declared
verifier should say so before the run. The reference compiler emits
`ING6006` as a **warning** — the declaration is correct and keeps its meaning
when verifiers gain an execution model, so it does not block a build.

This is a should, not a must: it is a property of a toolchain rather than of the
runtime contract.

## 4. Compatibility

A consumer written against Runtime 0.1 that reads `passed` will find the field
absent. That is deliberate: the alternative was leaving it present and wrong.

Cassettes move the other way: 0.1 documents keep working, and only re-recording
moves one to 0.2.

Everything else in [Runtime 0.1](./v0.1.md) applies without modification,
including the rule that events carry no timestamps and no durations, so a
replayed exchange still produces the same event sequence byte for byte.

## 5. What this does not do

It does not add a verifier execution model. `verify` still cannot be carried out
by anything, and an artifact that names one is still stating an unchecked
property — only now the run says so. An execution model for verifiers needs its
own RFC: a verifier is a tool call, a model call with a rubric, or host-provided
code, and choosing between those is a design rather than a bug fix.
