# Runtime Specification, version 0.6

Status: **Draft, implemented**. Normative for the reference interpreter and for
every backend that executes Agent IR.

Runtime 0.6 is [Runtime 0.5](./v0.5.md) plus one thing:

1. **a fan-out that overlaps** — the iterations of one `parallel map` may run
   concurrently, and what that is permitted to change is nothing.

Execution semantics, budgets, policy enforcement, cassettes, artifacts and every
other event are inherited from 0.5, 0.4, 0.3, 0.2 and 0.1 unchanged.
[Runtime 0.1 §5.1](./v0.1.md) keeps its wording exactly: a `parallel` node marks
an **opportunity** for concurrency rather than an obligation, and conformance
asserts the result and never the schedule. This document says what a backend that
takes the opportunity must not change, and states a ceiling that a backend which
declines it already satisfies.

Design reasoning is in
[RFC-0021](../../rfcs/0021-a-fan-out-that-overlaps.md).

## 1. Nothing here is a promise about speed

A backend that runs every `parallel map` body one element after another is
**conforming**, as it has been since 0.1. The Python backend does exactly that
and continues to.

Nothing in an artifact, in the IR or in the conformance suite asserts that
anything got faster. Every rule below asserts the opposite thing: that a run
which did overlap is indistinguishable, in its result and in its record, from one
which did not.

Consequently there is no `parallelMap` event, no field saying how many iterations
were in flight, and no way for a program to ask. A run's record does not say what
its schedule was, because a reader who could see that could come to depend on it.

## 2. The ceiling

### 2.1 What bounds it

A backend **must** bound the number of iterations of one `parallel map` that have
work in flight. A fan-out over a thousand elements opening a thousand connections
is not an implementation detail; it is a different program from the one the author
wrote.

Where the bound comes from is deployment configuration and **the artifact may not
carry it**. How many concurrent requests a service tolerates is a property of that
service and of the machine calling it: the same artifact against a hosted API and
against a model on a laptop wants different numbers, and an artifact stating one
would be wrong on one of them with nothing in the program to explain why. This is
the position [Runtime 0.5](./v0.5.md) and its predecessors already take on a wall
clock and on a price.

The reference implementation reads `[model] max-concurrency` from the manifest and
defaults to **4**. A backend is free to name its own knob; it is not free to have
none.

### 2.2 A ceiling of one, and what forces it

**Overlapping requires a second instance of every source of answers an iteration
touches.** A source that exists once cannot be shared without a lock, and a lock
does not overlap — it serialises, while making *which* iteration got which answer
depend on arrival order.

A backend **must** therefore execute a fan-out with a ceiling of one whenever the
body reaches something the run has only one of. At least these:

| Source | Why there is one | Consequence |
|---|---|---|
| A cassette | one recording, played in order | a replayed run — `ingot test`, or any run given a cassette — executes a fan-out sequentially |
| A supervisor channel | request and reply over one pair of pipes | a contained run executes a fan-out sequentially |
| A person | there is one operator | a body holding an `approval` or a `consult` node executes sequentially |

The first two are not exceptions carved out for cassettes and containment. They
are what it means for a run to have been given one provider and no way to make
another, and a backend that decides on that basis gets both without naming
either.

**A person is the one that must be checked against the artifact rather than the
arrangement.** A policy that requires approval for an effect makes the compiler
insert an `Approval` node ahead of the gated call
([Agent IR 0.1 §7](../ir/v0.1.md)), so a body that will stop for somebody says so
in the IR before the run starts. The reason is the reason `ING6005` already
refuses `consult` inside a `parallel` body
([Language 0.1 §6.4](../language/v0.1.md)): the order somebody is asked in is
**observable to them**, and a schedule-dependent order of questions is a
schedule-dependent experience for a person.

A backend **may** add to this list — the reference implementation also declines to
overlap a body that makes a tool `call`, because a tool host is one child process
([GAP-043](../../docs/gaps.md#gap-043)) — and a backend that overlaps nothing at
all satisfies this section trivially.

## 3. What overlapping may not change

### 3.1 The event stream is spliced in index order

Each iteration's events **must** reach the run's stream grouped by iteration and
ordered by **element index**, not by arrival. An implementation collects each
iteration's events privately and splices them when the fan-out completes.

So the record of a fan-out is byte-identical to the record of the same fan-out
executed one element at a time, and
`the_event_streams_agree_on_kind_and_order` compares a concurrent reference
interpreter against a sequential backend without either being adjusted for the
other.

The cost is a watcher's, and it is stated rather than hidden: **nothing from
inside a fan-out appears until the fan-out is done.**

### 3.2 No deltas from inside a fan-out

A backend **must not** emit deltas
([Runtime 0.3 §2](./v0.3.md)) from inside a fan-out it is overlapping. Several
answers interleaved fragment by fragment is not a live view of anything, and
labelling each fragment with its index would make it identifiable without making
it readable.

This changes nothing that is recorded, replayed or asserted on — a delta is not an
event — so it is decided on what a person watching sees, which is the only thing
it affects. `streams()` still governs the output-token ceiling: a provider that
streams keeps the larger one and streams into a sink that discards.

### 3.3 A recording is written in index order

A backend that records a fan-out **must** write the rows in element-index order,
whatever order the calls returned in. Two recordings of the same run against the
same inputs are then the same file, which is what makes a cassette reviewable and
diffable.

It is also what keeps §2.2's first row correct: a tape written in index order is a
tape that a run with a ceiling of one plays back row for row. **The cassette
format is unchanged, and the matching rule is unchanged** — position, verified by
digest, exactly as [Runtime 0.1 §10](./v0.1.md) states.

### 3.4 A failing iteration does not cancel the others

When an iteration fails, in-flight iterations **must** be allowed to finish, and
the fan-out then fails with **the first failure in index order** — not the first
in time.

Both halves refuse the same thing. Cancelling on the first failure makes the
amount a failing run spends depend on the scheduler, so the same artifact with the
same inputs produces two different bills. Reporting the first failure in time
makes *which* error an operator is shown depend on which socket answered first.

A policy denial inside a fan-out fails its iteration, and the fan-out then fails
by this rule. Nothing about enforcement moves: every check happens where it
happens today, at the node and before the effect.

### 3.5 A budget trips at the same total, at the same node

A `parallel map` executes its body once per element under either schedule, so the
same totals are reached. What a backend **must** also preserve is *where*:

* the run's counters **must** be charged in **index order**, so the iteration and
  the node that trip a ceiling are the ones sequential execution would have
  tripped;
* the events emitted before the trip **must** be the events sequential execution
  would have emitted, and no later ones.

A single shared counter incremented as calls return satisfies neither: whichever
thread arrives first becomes the iteration that failed. The reference
implementation gives each iteration private counters, bounded by the run's
remaining step budget so that no one iteration can outspend the run, and charges
their recorded totals into the run in index order once every iteration has
finished.

**What a fan-out spends before it notices is the whole fan-out**, because
iterations are drained rather than cancelled (§3.4). That is the price §3.4 pays
for a bill that does not depend on a scheduler, and it is stated rather than
discovered.

## 4. Static bounds and nesting

A `parallel` body may contain neither a state write, an emission nor a checkpoint
(`ING6005`), so an overlapping iteration observes nothing another wrote and
produces nothing another needs. A backend **may** rely on that; it **must not**
rely on it having been checked, and a backend that finds one of them in a body is
free to decline to overlap rather than to discard the effect.

A `parallel` nested inside a `parallel` **shares the run's one ceiling** rather
than multiplying it. The reference implementation achieves this by giving an
iteration no way to build providers of its own, so an inner fan-out has a ceiling
of one by §2.2 rather than by a rule about nesting.

A run may not stop inside a fan-out: a `checkpoint` cannot appear in a `parallel`
body, so §2.3 of [Runtime 0.5](./v0.5.md) is unaffected and a resumption never
lands mid-iteration.

## 5. Conformance

The suite's request shape is unchanged, and every case is served from a cassette —
so every conformance case runs with a ceiling of one by §2.2. This is deliberate:
a case pins the result and the record, both of which §3 requires to be identical
under either schedule, and a suite that overlapped would be testing the harness.

That a fan-out overlaps at all is therefore **not** a conformance property, and
cannot be: §1 says a sequential backend conforms. It is tested where it is
implemented.
