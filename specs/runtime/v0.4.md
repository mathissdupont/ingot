# Runtime Specification, version 0.4

Status: **Draft, implemented**. Normative for the reference interpreter and for
every backend that executes Agent IR.

Runtime 0.4 is [Runtime 0.3](./v0.3.md) with one change, in three parts:

1. a `verify` node may carry the **check itself**, and a backend that can
   evaluate an IR value **must** carry it out;
2. `notPerformed` narrows to mean **the artifact carries no check**, rather
   than *no backend has an execution model*;
3. a check that does not hold **ends the run**.

Execution semantics, budgets, policy enforcement, cassettes, artifacts and every
other event are inherited from 0.3, 0.2 and 0.1 unchanged. Nothing in this
revision adds an event kind, changes an event field, changes a cassette, or
changes the IR schema.

## 1. A `verify` node may carry its check

[Agent IR 0.2 §5](../ir/v0.2.md) permits `condition` on a `verify` node: the
verifier's body, with the call's arguments substituted for its parameters,
lowered as a pure value. It is the same `condition` a `branch` carries and the
same value forms.

A backend **must** evaluate a `verify` node's `condition` when one is present,
and **must** report:

| `condition` | Evaluates to | Outcome |
|-------------|--------------|---------|
| present | `true` | `passed` |
| present | `false` | `failed` |
| absent | — | `notPerformed` |

A `condition` that does not evaluate to a boolean is a malformed artifact, and
the backend **must** fail the run with that reason rather than choosing an
outcome.

A backend that reports `notPerformed` for a node carrying a `condition` is
**non-conformant**. This is the sentence that changes: Runtime 0.2 §1 allowed
any backend that answer, on the grounds that "Agent IR records a verifier's
name and signature and carries no representation of the check itself". For a
node with a `condition` that is no longer true, so the permission it justified
goes with it.

`notPerformed` keeps its meaning for a node without one, and keeps the reading
Runtime 0.2 §1 requires: **unknown**, folded into neither `passed` nor
`failed`.

### Why the check is in the artifact rather than beside it

The governing rule, and the one a later revision must not break:

> A `verified` outcome **must** be derivable from the run record alone.

A pure condition over values the run has already bound satisfies this by
construction: no provider, no clock, no host state, and no cassette entry take
part, so a replay reproduces every `verified` event byte for byte for the same
reason it reproduces a `branch`.

This is also what rules out the alternatives. A verifier implemented as
host-provided code produces an outcome that depends on a binary the record does
not describe. A verifier implemented as a model call with a rubric produces one
that depends on a cassette travelling beside the artifact — and a check that is
not deterministic is not what [Language 0.1 §5.2](../language/v0.1.md) defines a
verifier to be. A verifier that calls a *tool* could satisfy the rule, because
Cassette 0.2 records tool calls; that is left to a later revision, and this one
is written so it stays open.

## 2. A failed check ends the run

Runtime 0.2 §1 said "a `verify` node still does not stop a run". In 0.4 it does.

When a `condition` evaluates to `false`, a backend **must**:

1. emit the `verified` event with `outcome: "failed"`, **first**; then
2. end the run, naming the node and the verifier.

The ordering is normative. A record has to say what the check found before it
says the run ended, or the outcome cannot be attributed.

Artifacts emitted before the failing node **stay in the record**. They happened,
and removing them would make the record a summary rather than a history. No
statement after the failing node executes, and no output produced only after it
is emitted — so an agent whose flow verifies before it emits produces nothing on
a failed check, which is the ordering the reference compiler's `ING6007` warns
authors towards.

Ending the run is an **outcome**, not a crash: it is reported the way a denied
approval is reported, with the node and the verifier named.

### Why this is compatible in practice

No run reachable under 0.3 can produce `failed`: an artifact built by any
released compiler carries no `condition`, so every `verify` reports
`notPerformed` and nothing stops. The behaviour that changes is only available
to artifacts built after this revision, whose source opted in by giving a
verifier a body.

### Why not report and continue

The alternative was to let the run finish and mark its outcome, which gives a
consumer the artifact *and* the verdict against it. It was rejected because a
check that stops nothing is documentation, which is the state this revision
exists to leave. The judgement is not lost: the `failed` event is in the record
and the run's outcome names the verifier.

## 3. What a backend must do with a verifier it cannot execute

There is no such verifier. A `condition` uses only the value forms a backend
already evaluates for `branch` guards and `loop` guards, so any backend that
runs Agent IR at all can perform one.

A backend **must not** report `notPerformed` as a way of skipping a check it
finds inconvenient, and **must not** report `passed` for a node whose condition
it did not evaluate.

## Conformance

A backend claiming Runtime 0.4 must satisfy Runtime 0.3 and:

- [ ] `verify_with_a_true_condition_reports_passed`
- [ ] `verify_with_a_false_condition_reports_failed`
- [ ] `verify_without_a_condition_reports_not_performed`
- [ ] `a_failed_check_emits_its_event_before_the_run_ends`
- [ ] `no_statement_after_a_failed_check_executes`
- [ ] `artifacts_emitted_before_a_failed_check_stay_in_the_record`
- [ ] `a_non_boolean_condition_fails_the_run_as_malformed`
- [ ] `a_replayed_run_reproduces_every_verified_event_byte_for_byte`

## What this revision does not do

It does not give a verifier reach. A check is a pure expression over values the
run has bound: it can test fields, lengths and thresholds, and it cannot read
prose, call a tool, or resolve a URL. That is
[GAP-034](../../docs/gaps.md#gap-034), and closing it needs a verifier kind with
effects that still satisfies the derivability rule in §1.
