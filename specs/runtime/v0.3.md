# Runtime Specification, version 0.3

Status: **Draft, implemented**. Normative for the reference interpreter and for
any backend that serves a model completion incrementally.

Runtime 0.3 is [Runtime 0.2](./v0.2.md) with one change, in three parts:

1. a provider may deliver an answer **as it is produced**, and says whether it
   does;
2. that text travels on a **second channel** which is not the event stream and
   is not recorded;
3. the **output ceiling** for one call is decided by the transport rather than
   by the artifact.

Execution semantics, budgets, policy enforcement, cassettes, artifacts and every
event are inherited from 0.2 and 0.1 unchanged. Nothing in this revision adds an
event kind, changes an event field, or changes a cassette.

## 1. The streaming provider contract

[Runtime 0.1 §1](./v0.1.md) defines `ModelProvider` with one completion method.
0.3 adds two, both with defaults:

```rust
trait ModelProvider {
    fn name(&self) -> &str;
    fn complete(&mut self, request: &CompletionRequest)
        -> Result<CompletionResponse, ProviderError>;

    fn streams(&self) -> bool { false }

    fn complete_streaming(
        &mut self,
        request: &CompletionRequest,
        on_delta: &mut dyn FnMut(&str),
    ) -> Result<CompletionResponse, ProviderError> {
        self.complete(request)
    }
}
```

| Method | Meaning |
|--------|---------|
| `streams` | Whether this provider delivers an answer incrementally. |
| `complete_streaming` | Complete a request, handing text to `on_delta` as it arrives. |

A provider that answers all at once **must** report `streams() == false` and
need implement neither method. The default `complete_streaming` drops the deltas
and calls `complete`, which is the required behaviour for a provider with
nothing live to show: a cassette replay produces its answer at once, and a
provider **must not** invent fragments for an answer it did not receive in
pieces. A replay that emitted plausible deltas would make a replayed run
indistinguishable from a call that never happened.

`streams()` is a property of the provider and its transport, not of a call. It
**must** be answerable before a request exists, because a backend reads it to
build the request (§4). A provider that dispatches to others **must** report
`true` only when every provider it could dispatch to reports `true`; the answer
has to hold for whichever route ends up answering.

`complete_streaming` **must** return the same `CompletionResponse` that
`complete` would return for the same request. The deltas are additional, never a
substitute: the returned response is what the run uses (§3).

Fragments delivered to `on_delta` for one call **must** arrive in order and
**must** concatenate to the text of the answer. A provider **must not** reorder
them, deduplicate them, or deliver the same text twice.

A backend with nowhere to show text **may** call `complete` on a provider that
streams. The value **must** be the same either way.

### 1.1 Retrying a stream

A backend that retries a failed request **must not** retry a stream once any
part of the answer has been delivered. The caller has already shown that text to
somebody, and a second attempt would repeat it from the beginning.

Retries therefore cover only the window before the first delivered event, where
nothing has been observed and the attempt is genuinely repeatable. The reference
HTTP layer retries `429` and `5xx` responses, and stops retrying a stream at the
first event it delivers.

Resuming a broken stream is not defined here. A backend **must not** improvise
one by concatenating a second call's answer onto a first call's prefix: that is
a value derived from a fragment, which §3 forbids.

## 2. The live channel

`EventSink` gains two methods, both with defaults:

```rust
trait EventSink {
    fn emit(&mut self, event: RunEvent);

    fn delta(&mut self, node: &str, text: &str) {}
    fn settled(&mut self, node: &str, kept: bool) {}
}
```

`emit` carries the **event stream**: the record of what the run did. It is
ordered, it carries no timestamps and no durations, and a replay reproduces it
byte for byte ([Runtime 0.1 §9](./v0.1.md)).

`delta` and `settled` carry the **live channel**: text as a model produced it,
which is a property of the connection rather than of the run.

The rules:

* A delta **must not** appear in the event stream, **must not** be recorded in a
  cassette, and **must not** be asserted on by a conformance test (§2.1).
* Deltas for one node **must** be delivered in order and **must** concatenate to
  the text of that node's answer.
* `settled` **must** be called exactly once for a node that received at least
  one delta, after the run has decided whether the response became a value, and
  **must not** be called for a node that received none — with nothing shown
  there is nothing to settle.
* `kept` **must** be `true` only when the response was validated and bound. It
  is `false` whenever the accumulated text was discarded (§3).
* A backend **may** deliver no deltas at all. A replay delivers none, and that
  is correct: there is nothing live to watch.

### 2.1 A delta is not an event

[Runtime 0.1 §9](./v0.1.md) requires that replaying a recorded exchange produce
the same event sequence byte for byte, and that is what makes an event stream
assertable rather than merely inspectable. A recorded run against a service that
sent forty fragments, replayed with none, would differ by forty events.

Position matching depends on the same property. Replay pairs interactions by
position ([Runtime 0.1 §10](./v0.1.md)) and tool calls by position within their
own list ([Runtime 0.2 §2](./v0.2.md)). Events interleaved into the stream by a
transport move every position after them, by an amount that depends on how a
service happened to segment its answer.

Cross-backend comparison depends on it too. A backend that does not stream emits
the same events in the same order as one that does, precisely because a delta is
not among them.

A backend **must not** satisfy any of this by fabricating deltas for an answer
that arrived whole. The correct number of deltas for such an answer is zero.

### 2.2 Telling the two apart

A consumer **must** be able to distinguish the two channels without heuristics.
Where a backend renders both to one destination, a delta **must not** be
presented in the form an event is presented in.

The reference CLI writes both to standard error, because standard output carries
the run's artifacts and half-finished text must not be spliced into a pipeline
reading them. In its JSON form, a delta line and a settled line carry no `event`
key, and the event stream is exactly the set of lines that have one.

## 3. Partial responses

**A partial answer is not an answer.** This is the normative core of 0.3.

A backend **must** assemble the value a run uses from the finished response, and
**must** validate it whole, by the same code path a non-streamed response takes
([Runtime 0.1 §6](./v0.1.md)).

A backend **must not** derive a value from a fragment. Nothing downstream may
parse, repair, coerce or bind accumulated text before the response is complete,
and nothing may use it after a failure.

On failure the accumulated text **must** be discarded and the run **must** fail
exactly as an equivalent non-streamed call fails:

| Condition | Failure |
|-----------|---------|
| The answer was cut off at the token limit | `Truncated { limit }` |
| The answer did not match the declared type | `InvalidResponse` |

A backend **must not** widen or lower the declared type to make an incomplete
answer validate, and **must not** substitute a prefix for a response that never
finished.

Where at least one delta was delivered, the backend **must** call
`settled(node, false)` before failing, so a watcher can strike what it displayed
instead of leaving a half-finished answer on screen looking like a result.

The reason for the least clever rule available is that every alternative makes a
run's result depend on where a connection happened to stop. Two runs of one
prompt against one model would produce two answers, and the difference between
them would be a network event that nothing records and nobody can reproduce.
Truncation is the tempting case: the text on screen when a call hits its limit
is the beginning of a real answer, well formed and on topic. "The model stopped
here" is still not the same statement as "the model finished", and a truncated
JSON object that happens to close early and validate is a wrong answer that
passes every check.

### 3.1 One parser, two transports

A provider **must** accumulate its streamed pieces into a payload with the same
shape its non-streaming response has, and **must** hand that to the same parse
function.

This is what makes the guarantee structural: a streamed call and a whole-body
call produce identical values for the same content because the same code
produced them, and identical errors for the same bad content for the same
reason. A second parser on the streaming path would be a second answer to "did
this response validate", and the two would drift on exactly the inputs nobody
tested.

## 4. Output ceilings

A single call is bounded by a ceiling on output tokens:

| Transport | Ceiling |
|-----------|---------|
| Whole-body (`streams() == false`) | 16,000 output tokens |
| Streamed (`streams() == true`) | 64,000 output tokens |

A backend **must** choose between them by asking the provider, and **must not**
take the choice from the artifact. An artifact cannot select a ceiling and
**must not** be given a way to: the same artifact against a streaming provider
and a non-streaming one is the same program, and only the second has to keep the
smaller number.

The cap sent on one call is what remains of `budget.tokens` where the artifact
sets one, clamped to at least 1 and at most the ceiling the transport earned. A
backend **may** impose a smaller ceiling than the table states —
[Runtime 0.1 §8](./v0.1.md) allows stricter limits and forbids looser ones — but
**must not** use the streamed ceiling over a whole-body transport.

The whole-body number is not conservatism. A service that composes an entire
response before sending it holds the connection open for as long as the answer
takes, and several services refuse a larger `max_tokens` outright unless the
request streams.

The streamed number is a ceiling rather than no limit, because a `max_tokens`
above what a model accepts is a rejected request, and a number the interpreter
picked is easier to explain than a provider's HTTP 400.

Reaching the ceiling remains `Truncated`, unchanged from 0.1. Two backends may
therefore accept different answer lengths for one artifact; §6 names the case
that exists today.

## 5. Compatibility with 0.2 and 0.1

**A backend that satisfies Runtime 0.2 satisfies Runtime 0.3 with no change.**
Both provider methods and both sink methods are defaulted. A backend that
implements none of them reports `streams() == false`, keeps the 16,000-token
ceiling, delivers no live text, and emits exactly the event stream it emitted
before. There is nothing to migrate.

No event kind is added and no event field changes, so a consumer of the 0.2
event stream is unaffected. `cassetteVersion` stays `0.2`, the Agent IR version
is untouched, and an existing recording replays to the same bytes.

The `verified` outcome ([0.2 §1](./v0.2.md)), recorded tool calls
([0.2 §2](./v0.2.md)) and charged cost ([0.2 §3](./v0.2.md)) are unchanged. So
is everything in [Runtime 0.1](./v0.1.md), including §9's rule that events carry
no timestamps and no durations.

The one behaviour change on an existing artifact: against a provider that
streams, a call may ask for up to 64,000 output tokens, so an answer that used to
end the run with a truncation error may now complete.

Conformance items 1 to 8 of [Runtime 0.1 §13](./v0.1.md) stand. A backend
claiming conformance with Runtime 0.3 must additionally:

9. if it streams, produce the same value and the same error for the same content
   as it produces without streaming (§3.1);
10. emit no delta into the event stream and record none in a cassette (§2.1);
11. select the output ceiling from the transport and never from the artifact
    (§4).

## 6. What this does not do

**A contained run does not stream.** The interpreter runs inside the boundary
and the provider holding the credential stays outside it
([Runtime 0.1 §7.1](./v0.1.md),
[RFC-0005](../../rfcs/0005-the-contained-run.md)), so a delta would have to
cross the supervisor channel as a notification rather than as a reply. That is a
protocol change and it has not been made. A contained run delivers no live text
and keeps the 16,000-token ceiling. Its event stream is identical to an
uncontained run's, which is what §7.1 requires and which deltas do not threaten
([GAP-031](../../docs/gaps.md#gap-031)).

**The Python backend now streams too.** It did not when this revision was
written, so a response between 16,000 and 64,000 output tokens succeeded on the
reference interpreter and failed there. Both providers in the prelude report
`streams() == true` and rebuild the whole-body payload from the event stream
before parsing it (§3.1), and the ceiling is asked of the provider rather than
written into the generated program (§4). Closed as
[GAP-032](../../docs/gaps.md#gap-032).

**Deltas carry no determinism guarantee, deliberately.** Two runs of one prompt
may be chunked differently by the same service. No conformance test may assert a
delta's boundaries, its size, or how many arrived. This is not an omission; it
is what §2.1 means.

**A broken stream cannot be resumed** (§1.1), and a tool result is not streamed:
a tool returns one value, and nothing in [Runtime 0.1 §5.2](./v0.1.md) is
changed by this revision.

**Streaming is not concurrency.** One call is visible while it runs; two calls
still do not run at once. `parallel` executes sequentially as before
([Runtime 0.1 §5.1](./v0.1.md), [GAP-010](../../docs/gaps.md#gap-010)).
