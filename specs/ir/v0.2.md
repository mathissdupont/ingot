# Agent IR Specification, version 0.2

Status: **Draft, implemented**. Normative for `"irVersion": "0.2"`.

Agent IR 0.2 is Agent IR 0.1 plus portable source provenance for nodes, and an
optional `condition` on a `verify` node (§5). All 0.1 execution semantics remain
unchanged: `sourceSpan` is descriptive metadata only and must not affect node
ids, policy, budgets, runtime events, cassette request digests, or whether an
artifact executes.

The base document shape, node kinds, values, arguments, policy and budget rules
are inherited from [Agent IR 0.1](./v0.1.md). The machine-readable schema is
[`agent-ir.schema.json`](./agent-ir.schema.json).

## 1. Versioning

`irVersion` is the schema version. A backend that implements major version `0`
may accept both `0.1` and `0.2`; it must ignore `sourceSpan` for execution and
may use it for diagnostics, traces and editor navigation.

IR documents without `sourceSpan` remain valid. This preserves artifacts from
non-Ingot producers and older compilers.

## 2. Node source spans

Every node may carry:

```json
"sourceSpan": {
  "source": "main.ing",
  "start": 418,
  "end": 503
}
```

| Field | Meaning |
|-------|---------|
| `source` | Project-relative, slash-normalized source identifier |
| `start` | UTF-8 byte offset where the source range starts |
| `end` | UTF-8 byte offset where the half-open source range ends |

The source identifier must not be an absolute host path and must not contain
backslashes or `..` traversal components. A consumer that also has the source
text can derive line and column positions from the byte offsets.

The compiler should emit `sourceSpan` for every executable node it lowers from
Ingot source: calls, branches, loops, parallel maps, verification, state reads,
state writes, emitted artifacts and checkpoints. A backend or imported IR that
does not have source text should omit the field.

## 3. Compiler-inserted nodes

An `approval` node inserted before a gated call inherits the gated call's
`sourceSpan`. This keeps a human trace focused on the source expression that
caused the approval requirement, without changing the deterministic node id
sequence or policy decision.

## 4. Privacy and portability

`sourceSpan` must never reveal the build machine's absolute path. For a project
compiled from disk, source ids are relative to the entry file's directory:

- `main.ing`
- `shared/tools.ing`

For virtual sources, the compiler may use the virtual display name only when it
is already portable; otherwise it falls back to a basename.

## 5. `condition` on a `verify` node

A `verify` node may carry `condition`: the check itself, as a pure value.

```json
{
  "id": "n1",
  "kind": "verify",
  "verifier": "MinSources",
  "args": [
    { "name": "d",   "value": { "kind": "ref", "scope": "binding", "path": ["found"] } },
    { "name": "min", "value": { "kind": "literal", "type": "int", "value": 3 } }
  ],
  "condition": {
    "kind": "binary",
    "op": ">=",
    "lhs": {
      "kind": "builtin",
      "name": "len",
      "args": [ { "kind": "ref", "scope": "binding", "path": ["found", "sources"] } ]
    },
    "rhs": { "kind": "literal", "type": "int", "value": 3 }
  },
  "next": "n2"
}
```

This is not a new field and not a new value form. `condition` is already
declared on the node object in
[`agent-ir.schema.json`](./agent-ir.schema.json), where `branch` uses it, and
the value forms are the ones 0.1 defines. **The schema is unchanged**: a
`verify` node carrying a `condition` validates against it as written, which is
why this needs a paragraph rather than a version.

The value is the verifier's body with the call's arguments substituted for its
parameters, so `condition` refers to the run's own bindings and inputs rather
than to parameter names. In the example, the verifier's parameter `d` is gone:
`len(d.sources)` became a `ref` at `["found", "sources"]`.

`args` is kept beside `condition` even though every argument also appears
inside it. It is what a reader — a trace, an editor, a consumer of the record —
uses to show which values were checked, and it is what the compiler matched
against the verifier's signature.

A node without `condition` is a verifier declared with no body. It remains
valid, and [Runtime 0.4 §1](../runtime/v0.4.md) is where the two cases get their
outcomes.

## 6. Relationship to traces

Runtime event JSON is unchanged. A trace renderer can combine runtime
`agent:node` events with Agent IR `sourceSpan` and local project source to show
the originating file range. If local source is unavailable, it may still show
the portable source id and byte range.

## 7. Persistent memory

Two additions, both optional and both omitted when empty, so every artifact
compiled before them encodes byte for byte as it did and the IR version stays
`0.2`. See [RFC-0018](../../rfcs/0018-state-that-outlives-a-run.md).

### 7.1 `persistent` on the document

```json
"persistent": {
  "seen_urls": { "type": "string[]", "initial": [] },
  "visits":    { "type": "int",      "initial": 0 }
}
```

Sorted by field name, like `state`. `initial` is canonical JSON of the declared
type, resolved by the compiler from a literal.

The map is two things at once: the values a run starts from, and the declaration
a persistent store is checked against when one is opened.

### 7.2 `scope` on a store node

`state.read` and `state.write` gain an optional `scope`:

```json
{"id": "n1", "kind": "state.write", "field": "visits", "scope": "memory",
 "value": {…}, "next": "n2"}
```

Absent means working memory, which is what every artifact written before this
section meant. `"memory"` is the only other value.

A backend that ignores `scope` writes a persistent field into working memory and
loses it at the end of the run. That is a conformance failure, not a degraded
mode: the `memory-initial` case pins it.

### 7.3 `resumable` on a `checkpoint`

```json
{"id": "n7", "kind": "checkpoint", "label": "sources-collected",
 "resumable": true, "next": "n8"}
```

True only for a checkpoint at the top level of a flow. Omitted when false, so a
nested checkpoint encodes exactly as it always has.

A top-level one does not: it gains the line, and the artifact's digest changes.
That is the only place persistent memory and resumption move an existing
artifact's bytes.

The flag is computed by the compiler and is not a hint: a backend that supports
resumption may stop at a `resumable` checkpoint and must not stop at any other.
See [Runtime 0.5 §2](../runtime/v0.5.md).
