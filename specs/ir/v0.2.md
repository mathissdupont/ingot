# Agent IR Specification, version 0.2

Status: **Draft, implemented**. Normative for `"irVersion": "0.2"`.

Agent IR 0.2 is Agent IR 0.1 plus portable source provenance for nodes. All
0.1 execution semantics remain unchanged: `sourceSpan` is descriptive metadata
only and must not affect node ids, policy, budgets, runtime events, cassette
request digests, or whether an artifact executes.

The base document shape, node kinds, values, arguments, policy and budget rules
are inherited from [Agent IR 0.1](./v0.1.md). The machine-readable schema is
[`agent-ir.schema.json`](./agent-ir.schema.json).

## 1. Versioning

`irVersion` is the schema version. A backend that implements major version `0`
may accept both `0.1` and `0.2`; it must ignore `sourceSpan` for execution and
may use it for diagnostics, traces and editor navigation.

IR documents without `sourceSpan` remain valid. This preserves artifacts from
non-Ingot producers and older compilers.

## 2. Node source spans

Every node may carry:

```json
"sourceSpan": {
  "source": "main.ing",
  "start": 418,
  "end": 503
}
```

| Field | Meaning |
|-------|---------|
| `source` | Project-relative, slash-normalized source identifier |
| `start` | UTF-8 byte offset where the source range starts |
| `end` | UTF-8 byte offset where the half-open source range ends |

The source identifier must not be an absolute host path and must not contain
backslashes or `..` traversal components. A consumer that also has the source
text can derive line and column positions from the byte offsets.

The compiler should emit `sourceSpan` for every executable node it lowers from
Ingot source: calls, branches, loops, parallel maps, verification, state reads,
state writes, emitted artifacts and checkpoints. A backend or imported IR that
does not have source text should omit the field.

## 3. Compiler-inserted nodes

An `approval` node inserted before a gated call inherits the gated call's
`sourceSpan`. This keeps a human trace focused on the source expression that
caused the approval requirement, without changing the deterministic node id
sequence or policy decision.

## 4. Privacy and portability

`sourceSpan` must never reveal the build machine's absolute path. For a project
compiled from disk, source ids are relative to the entry file's directory:

- `main.ing`
- `shared/tools.ing`

For virtual sources, the compiler may use the virtual display name only when it
is already portable; otherwise it falls back to a basename.

## 5. Relationship to traces

Runtime event JSON is unchanged. A trace renderer can combine runtime
`agent:node` events with Agent IR `sourceSpan` and local project source to show
the originating file range. If local source is unavailable, it may still show
the portable source id and byte range.
