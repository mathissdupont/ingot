# Agent IR Specification, version 0.4

Status: **Draft, implemented**. Normative for `"irVersion": "0.4"`.

Agent IR 0.4 is Agent IR 0.3 plus one optional field on a node, `fallback`.
Everything else — the document shape, values, arguments, node kinds, policy and
budget rules, source spans, persistent memory — is inherited unchanged from
[Agent IR 0.3](./v0.3.md), [0.2](./v0.2.md) and [0.1](./v0.1.md). The
machine-readable schema is [`agent-ir.schema.json`](./agent-ir.schema.json).

Designed in [RFC-0022](../../rfcs/0022-a-failure-an-iteration-can-absorb.md).

## 1. Versioning

`irVersion` is the schema version. A backend that implements major version `0`
may accept `0.1` through `0.4`.

**0.4 is additive in the strong sense: it adds no node kind and changes no
field.** A node carrying no `fallback` encodes byte for byte as it did at 0.3, so
every artifact any earlier 0.x produced is a valid 0.4 artifact, and recompiling
one produces a document whose only difference is the `irVersion` line itself.

An 0.3 reader handed an 0.4 document is in the position `sourceSpan` and
`condition` put an 0.1 reader in: the field it does not know is one it would
*ignore*, and ignoring this one is not safe. A node with a `fallback` describes a
failure the program said what to do about; a reader that dropped the field would
stop the run where the program said to continue. So a reader that does not
implement §2 must refuse an 0.4 document rather than read the parts it recognises.

Producers stamp the version they implement rather than the lowest one a document
happens to fit.

## 2. The `fallback` field

```json
{
  "id": "n1",
  "kind": "tool.call",
  "binding": "writeup",
  "tool": "mcp:fs.read_file",
  "effects": ["filesystem_read"],
  "args": [
    { "name": "path", "value": { "kind": "ref", "scope": "binding", "path": ["item"] } }
  ],
  "fallback": { "kind": "literal", "type": "string", "value": "no write-up was filed" },
  "next": null
}
```

`fallback` is a [`Value`](./v0.1.md) — the same pure-expression form `condition`,
`source` and `prompt` use. **It is not a node id, and that is the entire design:**
the fallback reaches nothing, so it spends no step, widens no policy, and the
graph a backend walks does not branch here.

| Rule | |
|---|---|
| Where it may appear | `llm.call`, `tool.call`, `agent.call` — and nowhere else |
| What it holds | a pure `Value` |
| When it is evaluated | only when the attempt failed, and only when §3 permits |
| What it produces | the value the node's `binding` takes |

A `fallback` on any other node kind makes the artifact **malformed**. A runner
must refuse such a document; the reference interpreter refuses it before the run
starts rather than when the node is reached, so an artifact that is going to be
refused is refused before it spends anything.

## 3. What a fallback may not absorb

This is the rule the field's safety rests on, and it is normative. Full statement
and the reasoning: [Runtime 0.7 §2](../runtime/v0.7.md).

A fallback stands in for a failure of the **attempt**. It must **not** stand in
for:

* a capability the artifact's policy denies, or for which it grants no rule;
* a budget that ran out;
* an approval a person refused;
* a `verify` whose property did not hold;
* a malformed artifact;
* a recording that no longer matches this run;
* a missing credential, an unusable model, or a tool no host provides.

A backend that absorbed the first would make `deny` advisory. A backend that
absorbed the sixth would let a test pass on a digest of defaults after somebody
edited a prompt.

## 4. Steps, tokens and cost

**The attempt is the step, charged exactly once**, whether or not the fallback is
used — so `budget.steps` bounds a flow with fallbacks exactly as it bounds one
without. The fallback is a value, and evaluating a value is not a step.

Tokens and cost are charged from what a call *returned*. A call that failed
returned nothing, so it adds neither. That is inherited behaviour rather than a
rule of this version, and it is worth stating because it has a consequence: **a
run's recorded token total can be lower than what the provider actually billed**,
when an answer arrived and was then rejected. The record says what the run used,
not what the transport spent.

## 5. Recording and replay

The cassette format does not move; it is still **0.3**.

A failing tool call is already recordable: `ToolExchange` carries `error` and has
since cassette 0.2. A model answer that did not match its declared type is
recorded as the value it was — the recording is made before the run validates it —
so replaying serves the same failure and the fallback runs again, reproducing the
run's event stream exactly.

A model call that returned *no* value — unreachable, refused, timed out — is not
recordable at any cassette version, because `Interaction` records a value and has
no field for an error. See [GAP-046](../../docs/gaps.md#gap-046).

## 6. Events

One new event, `fallbackTaken`. See [Runtime 0.7 §2.2](../runtime/v0.7.md).

## 7. Backends

Every backend that accepts an 0.4 document must implement §2, §3 and §6. There is
no partial support: a backend that read `fallback` and ignored §3 would turn the
artifact's guarantees into default values, which is worse than refusing the
document.

Both shipped backends implement it, and the conformance case `fallback-taken`
holds them to the same event stream.
